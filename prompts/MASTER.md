# PROJECTHELLO — Master Prompt

你正在进入 PROJECTHELLO 管理的项目体系。

PROJECTHELLO 的职责不是替代各个正式项目仓库，而是保存跨项目的长期上下文、项目简介、原始想法、启动规则和给 AI 的统一工作约定。

## 总原则

1. **先理解，再修改。**
   - 进入任何项目后，先阅读该项目已有的 README、AGENTS、PROJECT、STATUS、ROADMAP 或等价文件。
   - 先检查现有代码与 Git 状态，不要假设当前项目需要重写。

2. **不要破坏已有内容。**
   - 优先增量修改。
   - 不删除已有功能、文件、历史约定或用户数据，除非任务明确要求。
   - 大改前先确认旧实现为什么存在，并尽量保留可工作的部分。

3. **项目编号是长期身份。**
   - Project01–Project100 代表固定项目槽位。
   - 项目名称可以变化，但编号应尽量保持稳定。
   - 不要自行交换、复用或覆盖已有编号。

4. **事实与想法分开。**
   - 已实现、正在实现、已验证、仅构思、已否决/暂缓必须明确区分。
   - 不把 quick/demo 的结果写成正式结论。
   - 不把“可能做”写成“已经做”。

5. **让下一位 AI 能接手。**
   - 重要改动后留下足够的上下文：做了什么、为什么、测试了什么、还剩什么。
   - 若项目已有 STATUS.md / AGENTS.md / ROADMAP.md，优先更新这些文件，而不是额外创造重复文档。

6. **保持项目边界。**
   - PROJECTHELLO 保存总览、想法和启动信息。
   - 正式代码、测试、CI、部署和大型资产应留在各自独立项目仓库。

## AI 开始一个项目时

按下面顺序工作：

1. 确认当前项目编号与项目名称。
2. 阅读 PROJECTHELLO 中对应的项目简介。
3. 阅读目标项目仓库自己的 README / AGENTS / STATUS / ROADMAP。
4. 检查仓库结构和 Git 状态。
5. 用一句话复述当前项目目标。
6. 找到本次任务最小而完整的改动范围。
7. 实施。
8. 运行相关测试或最接近真实使用的验证。
9. 汇报：
   - Changed
   - Verified
   - Remaining
   - Next

## 新项目启动规则

当用户提出一个新项目，而尚未指定项目编号时：

- 先寻找空闲的 ProjectXX 槽位；
- 不覆盖已有项目；
- 为新项目建立简短项目卡，至少记录：
  - 一句话目标
  - 为什么值得做
  - 第一版应该证明什么
  - 明确不做什么
  - 当前下一步
- 在真正开始开发前，再将代码工作放入对应独立仓库。

## 工作风格

- 默认直接做事，少写空泛计划。
- 复杂任务可以先给短计划，但随后应进入执行。
- 不因为“重构更漂亮”就重写大量已工作的代码。
- 优先可验证、可回滚、可交接的改动。
- 项目越大，越需要留下清楚的状态，而不是靠聊天记录维持上下文。

## 对不确定信息的处理

若某个项目编号、名称、状态或历史不确定：

- 写成 `Unknown / To verify`；
- 不凭空补全；
- 保留原始信息，等待后续核对。

这个 Master Prompt 是所有项目的共同基线。各项目可以在自己的项目卡和仓库内拥有更具体的规则；若发生冲突，以用户当前明确要求和项目内更具体的约定为准。
